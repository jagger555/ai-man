# 面向回答准确率的知识库检索增强设计

## 背景

当前项目是 AI 数字人景区导览 MVP，核心目标是让数字人尽量准确回答游客关于景区的问题，并能展示可追溯的知识来源。现有知识库主要来自 `data/sample_scenic/knowledge.md`，管理后台新增文档默认以 JSON 文件保存；检索阶段在运行时构造 chunk，并用 jieba 分词、关键词命中和规则加权排序。

这个方案不把“换数据库”作为主要目标。数据库升级的价值在于支撑更稳定的知识文档管理、结构化分块索引和可复现的检索链路。真正影响回答准确率的是：知识分块质量、问题分类、景区实体识别、检索排序规则，以及回答阶段对来源片段的严格约束。

## 目标

- 提升事实类、路线类、票务类、时间类、位置类、历史文化类问题的召回准确率。
- 让每次回答都尽量基于明确的知识片段，并保留来源、分数和可靠性判断。
- 降低数字人编造答案的概率；知识库没有可靠依据时，明确给出低置信度兜底。
- 将知识文档和可检索 chunk 持久化，便于后台维护、重建索引和后续扩展向量检索。

## 非目标

- 不在第一阶段引入 Chroma、FAISS、Qdrant、Milvus 等向量库。
- 不在第一阶段依赖 embedding 模型作为主检索方式。
- 不重写整个问答链路或数字人链路。
- 不做通用百科问答，仍然聚焦景区导览知识库。

## 推荐方案

采用 SQLite 主存储加结构化 chunk 索引：

```text
知识文档
  -> knowledge_documents
  -> chunk 构建和标签提取
  -> knowledge_chunks
  -> 问题分类和实体识别
  -> 分类过滤 / 加权排序 / 关键词打分
  -> top chunks
  -> LLM 基于来源片段生成回答
  -> 数字人播报可信回答或低置信度兜底
```

SQLite 用于保存知识文档和 chunk 索引。检索仍优先使用可控的规则化方法：问题分类、景区实体词典、关键词命中、类别加权和来源片段评分。这样比直接上向量库更符合当前比赛 MVP 的稳定性要求，也更容易解释系统为什么给出某个答案。

## 数据模型

### knowledge_documents

保存后台可维护的知识文档。

- `id`: 文档 ID。
- `title`: 标题。
- `category`: 文档分类，如讲解词、历史文化、FAQ、游览须知、路线。
- `content`: 原始正文。
- `source_name`: 来源文件名或人工录入来源。
- `status`: `active`、`draft`、`archived`。
- `created_at`: 创建时间。
- `updated_at`: 更新时间。

### knowledge_chunks

保存实际参与检索的知识片段。

- `id`: chunk ID。
- `document_id`: 所属文档 ID。
- `text`: 可检索片段文本。
- `chunk_type`: 片段类型，如 fact、route、notice、faq、history。
- `entities_json`: 景点、建筑、路线名等实体。
- `keywords_json`: 检索关键词。
- `question_categories_json`: 适合回答的问题类别，如 height、schedule、ticket、route、location、culture、recommend。
- `status`: 是否参与检索，跟随文档状态或单独禁用。
- `created_at`: 创建时间。
- `updated_at`: 更新时间。

第一阶段不存 embedding，但表结构允许后续新增 `embedding_model`、`embedding_vector_path` 或单独的向量索引表。

## 检索策略

检索入口仍保留 `KnowledgeBase.search(query, limit)`，避免大范围改动调用方。内部策略调整为：

1. 对用户问题做清洗和分类，识别问题类型，例如高度、开放时间、票价、路线、位置、历史文化、推荐。
2. 用景区实体词典识别问题中的景点、建筑、表演、路线等实体。
3. 从 `knowledge_chunks` 中读取 active chunk，按问题类型和实体进行过滤或加权。
4. 使用 jieba 分词、关键词命中次数、实体重合度、类别匹配度计算综合分。
5. 返回 top chunks，并保留分数、来源文档、类别和实体信息。

事实型问题要优先召回短 chunk，路线类问题可以召回较长的完整路线 chunk。这样避免“问大佛高度却召回游览路线”或“问开放时间却召回历史介绍”。

## 回答约束

`AnswerService` 继续负责组合检索结果、Prompt 和 LLM。为了提升准确性，需要强化以下规则：

- 只有当 top chunks 达到最低分数或最低来源数量时，才允许生成确定性回答。
- Prompt 明确要求模型只基于给定来源回答，不要补充知识库之外的信息。
- 当来源不足时，返回低置信度兜底，让数字人说明“当前知识库没有足够可靠的信息”。
- 回答结果继续记录来源片段、置信度、可靠性、响应时间和模型状态，便于后台分析。

## 后台维护

后台知识库管理继续支持新增、编辑、上传、归档、搜索和分类统计。文档保存后触发 chunk 重建：

- 新增 active 文档：写入 `knowledge_documents`，生成对应 `knowledge_chunks`。
- 更新文档：更新原文，删除或停用旧 chunk，重建新 chunk。
- 归档文档：文档状态改为 archived，对应 chunk 不再参与检索。
- 上传 txt、md、docx：先解析正文，再按同一套 chunk 构建流程入库。

## 测试与验收

必须先建立小型标准测试集，覆盖至少以下类型：

- 高度和尺寸类问题。
- 开放时间、演出时间类问题。
- 票务、优惠和注意事项类问题。
- 路线推荐和人群偏好类问题。
- 景点位置和游览顺序类问题。
- 历史文化、寓意和特色类问题。

验收不只看接口是否返回结果，而要看 top 1 或 top 3 是否召回正确来源片段。只有来源片段正确，数字人的回答准确率才有基础。

## 风险

- 如果只迁移到 SQLite，但 chunk 和排序规则不变，准确率不会明显提升。
- 规则检索依赖实体词典和分类规则，初始词典不完整会影响召回。
- 过长 chunk 会导致模型回答混杂，过短 chunk 会丢失上下文，需要用测试集校准。
- 当前代码中部分中文常量存在乱码迹象，后续实现时需要同步修正，否则分类触发词可能失效。

## 落地顺序

1. 建立标准测试集和检索评测脚本，先明确准确率基线。
2. 设计 SQLite schema，并实现文档与 chunk 的读写。
3. 实现 chunk 构建器，按段落、FAQ、路线、事实描述生成不同类型 chunk。
4. 增强问题分类、实体词典和评分规则。
5. 将后台新增、编辑、上传、归档接入 SQLite 和 chunk 重建。
6. 强化回答阶段的来源约束和低置信度兜底。
7. 用测试集回归验证，再考虑是否需要 embedding 或向量库作为补充召回。

## 决策

当前阶段采用 SQLite 加结构化分块索引，不直接引入向量库。这个方案优先服务于数字人准确回答景区问题，同时保持依赖轻、部署稳、演示可解释，并为后续向量检索预留扩展空间。
